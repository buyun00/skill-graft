# OZDQP Skill Hub：系统设计与理念

> 状态：本机实验可用，未推远端，尚未做成团队共享服务。
> 仓位：`E:\ozdqp-skill-hub`（独立 Git 仓库，不要提交进 ozdqp 游戏仓）
> 管理页已删除，HTTP API 在 `server/index.mjs`（:18765），以后重做前端。
> 本文写于 2026-08-18，对应这次本地搭起来并跑通挂接的尝试。

## 1. 要解决什么问题

游戏仓（ozdqp）在 Git 上有一套官方 Skill / agent / 规则目录，体积大、条目多、和当前客户端实际工作方式不完全一致。

本机另外整理出一套更小的 **3 Skill** 架构，更贴近现在怎么写代码、改 UI、做 Git。这套整理**不适合直接推回游戏仓主干**：它是个人/本机工作流，不是全员统一的官方目录。

于是出现三个具体矛盾：

1. **本机想用 3 Skill，游戏仓多个 worktree 却各自带着官方目录。** 每个新签出的分支都会把官方 Skill 树再摊到磁盘上。
2. **3 Skill 若复制到每棵树上，改一处就要同步多处。** 复制会漂，链接才是一份真相。
3. **别人 `fetch`/`pull` 上来的官方 Skill 更新，不该在功能分支上当场归类。** 功能对话应该继续写业务；“要不要吸收这条官方 Skill”是中心仓的事。

Skill Hub 就是为这三件事建的本机中心仓：一份本地 Skill 权威源，游戏树只挂链接；官方更新进 inbox，由面板决定；危险的剥离/挂接必须经面板里的 Codex 对话，而不是静默脚本。

## 2. 设计理念

### 2.1 权威源只有一份

本地工作流的真相在中心仓，不在任何一棵游戏 worktree 里。

| 东西 | 权威位置 | 游戏树上的形态 |
|---|---|---|
| `ozdqp-development` | `skills/ozdqp-development` | Junction |
| `ozdqp-ui-development` | `skills/ozdqp-ui-development` | Junction |
| `ozdqp-git-workflow` | `skills/ozdqp-git-workflow` | Junction |
| `AGENTS.override.md` | 仓根 | HardLink（符号链接在本机权限下常失败） |
| overlay 脚本/hook/提示词 | `overlay/` | Junction 到 `.codex/local-overlay` |

改 Skill 只改中心仓。已挂接的树立刻看到同一份文件，不用拷贝、不用发版、不用在游戏仓提交这些文件。

### 2.2 游戏仓不持有本地工作流副本

中心仓是**另一个 Git 仓库**，不嵌在游戏仓里。这样：

- 游戏仓 `git status` 不会被 3 Skill 的编辑污染
- 以后可以把中心仓推到 GitLab，做成团队 Skill 服务，而不必先说服主干接受这套目录
- 官方 Skill 仍然存在于游戏仓的 Git 历史里，只是挂接后在**磁盘上**被拿掉

官方助手文件用 `skip-worktree` 从工作区摘掉，不是从 Git 里删掉。`Restore` 还能临时放回来，给 `fetch`/`merge` 用。

### 2.3 链接，不复制

同盘用 **Junction** 挂目录，文件优先符号链接、失败则 **HardLink**。

这不是为了炫技，是为了满足“改中心仓 = 所有已挂树同时更新”，同时避开 Windows 上普通用户创建文件符号链接经常失败的问题。面板判断 override 是否接通时，不能只看 `realpath`，必须能认出 HardLink（比 inode）。

### 2.4 危险动作走对话，幂等修复才走脚本

| 动作 | 谁来做 | 为什么 |
|---|---|---|
| 某棵树**第一次**剥官方 Skill、改挂中心仓 | 面板 Codex 对话（`attach`） | 要侦察脏文件、旧 overlay、重名差异；不能静默改盘 |
| 已挂接的树链接断了 | `attach-library.ps1` 可直接修 | 目标已知、操作幂等 |
| `fetch`/`pull` 官方 Skill | hook 只 **ingest 到 inbox** | 功能分支对话禁止在本树做语义归类 |
| 采用 / 并入 / 拒绝 inbox | 面板按钮 → `promote-inbox.ps1` | 决策在人，执行是机械的 |
| 用 Codex 改某条 Skill | 面板 `edit` 对话 | 改的是中心仓，不是游戏仓 |

原则：**脚本负责可逆、可重复的磁盘动作；对话负责判断和第一次切换。** 不要把“跑通脚本”当成“切换完成”。

### 2.5 Codex 只活在中心仓进程里

面板里的 Codex：

- 工作目录永远是中心仓
- 允许改 Skill / inbox / adopted / override / overlay
- **禁止写游戏仓业务代码**
- 需要碰某棵游戏树时，用 `--add-dir` 打开那一棵，仍然不是去改玩法

游戏仓里的日常开发对话继续用 3 Skill 写业务。两套对话不要混。

### 2.6 先挂一棵，再谈自动

现有的旧 worktree 默认不自动处理。`do-not-auto-attach.txt` 是黑名单。新签出是否自动拉起 attach 对话，由 `ozdqp.skillHubAutoAttach` 控制，默认关。这次实验只主动挂了：

- `E:\ozdqp-main-ntfs`（先试点）
- `E:\ozdqp-main-fix`（经面板对话切换）

没有去扫盘批量改其它树。

### 2.7 面板是控制面，不是第二套 CLI

人要看的是：哪些树挂了、inbox 里有什么、Codex 正在说什么。人要做的是：开任务、续聊、拍板。

因此 Codex 必须**嵌在页面里**：不弹新窗口、不问权限、日志用 SSE 往上推。一轮 `exec` 结束后会话进入 `waiting`，同一条 Codex session 可以 `resume`，而不是每次都新开一个失忆的进程。

## 3. 两套 Skill 分别是什么

### 3.1 官方目录（游戏仓 Git 跟踪）

签出后会出现在例如：

- `.agents/skills/**` 下大量官方条目
- `.claude/**`
- `.codex/skills/**`、`.codex/agents/**`、`.codex/scripts/**`
- 根上的 `AGENTS.md` / `CLAUDE.md`

优点：和远端主干一致，别人推上来的更新走正常 Git。  
缺点：对当前客户端日常开发过重，且和本机整理过的路由冲突。

### 3.2 本机 3 Skill（中心仓持有）

| Skill | 何时用 |
|---|---|
| `ozdqp-development` | 实现：理解 → 计划 → 实现 → 验证；按需读调试/Unity 约定/模块边界/完成验证 |
| `ozdqp-ui-development` | Unity UI / Prefab / 绑定；先定检查强度（完整规范化 / 定点 / 不触发组件规范） |
| `ozdqp-git-workflow` | 分类、提交、同步、worktree；官方 Skill 更新只交班到面板 |

另有一条**不属于中心仓**的 `unity-skills`：它是游戏工程生成目录的 Junction（`baloot_client/.agents/skills/unity-skills`），走 UnitySkills 本地 REST。挂接时必须保留，不能剥掉。

`AGENTS.override.md` 规定任务路由和 Unity 后端。游戏树根上的 override 必须指向中心仓那一份。

### 3.3 为什么不把 3 Skill 上传到游戏仓

- 它是本机整理结果，和官方目录同名或职责重叠时会打架
- 上传等于强迫所有人、所有 worktree 立刻改工作方式
- 中心仓独立演化，以后要共享，推的是 hub，不是往游戏仓塞另一棵 Skill 树

官方更新的吸收路径是：**inbox → 面板决定 adopt / merge / reject**，而不是“把本地 3 Skill 整包覆盖上去”。

## 5. 运行时怎么串起来

```text
                    ┌──────────────────────────────┐
                    │     E:\ozdqp-skill-hub       │
                    │  3 Skill / inbox / overlay   │
                    │  面板 :18765  + 内置 Codex    │
                    └──────────────┬───────────────┘
           Junction/HardLink       │         hook ingest
        ┌──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
  ozdqp-main-ntfs            ozdqp-main-fix              其它未挂树
  已挂、写业务               已挂、写业务                 仍用分支自带
        │                          │
        │  fetch/pull 官方 Skill    │
        └──────────► reference-transaction
                     git show → hub/skills/inbox
                     功能对话只说：去开面板
```

### 5.1 面板

- 查询：`status` / `list-worktrees` / `list-skills` 在 `src/core`，HTTP 与 `npm run hub` 共用。
- 启动：`overlay/start-panel.ps1`。先编译核心，再用 WMI `Win32_Process.Create` 拉起，避免被父进程的 Windows Job Object 一起杀掉。
- 前端：Vue 3，DaisyUI `night` + `card glass`，暗色毛玻璃。中间换过 Naive / PrimeVue / Ant，最后留在 DaisyUI，因为只要原生玻璃质感，不要重皮肤。
- 页面：运行、工作区、Skills、待审、历史。
- 工作区扫描：读 `scan-roots.txt` 下一层目录，认出带 `AGENTS.md` + `baloot_client` 的客户端仓，再对每个 clone 跑 `git worktree list`。按本地最近改动时间排序，显示磁盘目录名。

### 5.2 内置 Codex

面板不调用 `codex.cmd`（Windows 上 `spawn` 会 EINVAL），而是：

```text
node %APPDATA%\npm\node_modules\@openai\codex\bin\codex.js exec ...
```

约束是踩坑踩出来的：

- `stdio: ['ignore', 'pipe', 'pipe']`。stdin 若开着，Codex 会停在 “Reading additional input from stdin...”
- 提示词走 argv，不走管道，避免 “stdin is not a terminal”
- 沙箱 `danger-full-access` + `--dangerously-bypass-approvals-and-sandbox`，否则 `--add-dir` 加游戏树会被拒
- `--skip-git-repo-check` 不是因为 hub 不是 Git 仓，而是给 exec 一条稳定的非交互路径
- 日志文件 + SSE `/api/codex/session/stream`，页面实时刷
- 从输出里抓 `session id:`，成功一轮后状态是 `waiting` 不是 `completed`
- 续聊：`codex exec resume <session-id> <message>`，对应 `POST /api/codex/resume`

四种任务模板在 `overlay/prompts/`：

| kind | 模板 | 用途 |
|---|---|---|
| chat | `chat.txt` | 改中心仓任意允许路径 |
| edit | `edit.txt` | 只改指定 Skill |
| attach | `attach.txt` | 剥官方、挂本地 |
| detach | `detach.txt` | 拆链接、Restore 官方树 |

`codex exec` **一轮一退**是正常的。对话连续性靠 resume，不靠长驻交互进程（交互模式在无 TTY 的面板子进程里不稳定）。

### 5.3 挂接与剥离

`manage-skill-visibility.ps1 -Mode Disable`：

- 保留 `.agents/skills` 下三个项目 Skill、`unity-skills`、以及 hub `skills/adopted` 里的名字
- 其余官方 `.agents/skills/*`、`.claude/**`、`.codex/skills|agents|scripts`、`cursor-rules.env` 从磁盘拿掉，并打上 `skip-worktree`

`attach-library.ps1`：

- 先比 3 Skill / override 和 hub 是否一致
- 不一致且带 `-PreferLibrary`：以 hub 为准换成链接
- `-PromoteFromWorktree`：把树上的版本拷回 hub（面板 attach **禁止**这条，避免旧副本污染权威源）
- 现成的实体 `.codex/local-overlay` 会先备份成 `.codex/local-overlay.pre-hub-<时间>`
- `-ConfigureGit` 写 hook 和 ozdqp.* 配置
- 把路径追加进 `attached-worktrees.txt`

`post-checkout`：已在名单里的树只修链接；新树仅当 `skillHubAutoAttach=true` 时拉起 Codex attach，不静默剥离。

### 5.4 官方更新怎么进中心仓

`reference-transaction` 在 `committed` 且 `ozdqp.skillWatchEnabled=true` 时，把 payload 交给 `analyze-remote-skill-update.ps1`：

1. 只看远端引用
2. 按 pathspec 抽出 `.agents/.codex/.claude/skills` 以及根 `AGENTS.md` / `CLAUDE.md`
3. `git show` 到 `skills/inbox/<name>/`
4. 写入 `skill-review/state.json` 和 history
5. 可选再 dispatch 一条中心仓 Codex（分析建议，不是自动 adopt）

功能分支上的 Git Skill 只做一件事：告诉人去开 http://127.0.0.1:18765/ 。

面板拍板：

- **采用**：inbox 整棵搬到 `skills/adopted`，已挂接的关联游戏树补一条 Junction
- **并进**：标记并入某个 3 Skill 参考文件，删掉 inbox 副本（真正改参考内容应再开 `edit` 对话）
- **拒绝**：丢掉 inbox

## 6. 这次尝试实际做了什么

按时间，都是本机中心仓上的迭代，没有把 hub 推到 GitLab，也没有改游戏仓玩法代码。

1. **立项**  
   承认 3 Skill 不能上传；决定新开独立仓当主库；游戏树只挂链接；先只挂当前树。

2. **仓和链接模型**  
   建 `E:\ozdqp-skill-hub`。3 Skill 与 overlay 用 Junction，`AGENTS.override.md` 用 HardLink。面板用 inode 识别 HardLink。

3. **ingest 与交班**  
   hook 把官方 Skill 更新写进 inbox。功能分支只交班，不在本树归类。

4. **面板**  
   Node 静态站 + JSON API。扫 E/F/用户目录下的客户端仓和它们的 worktree。启动必须脱离 Agent Job，否则面板随对话结束一起死。

5. **把 Codex 塞进页面**  
   从“弹 Windows Terminal 新窗”退到“进程内 exec”。中间修过：WT 参数被拆、`--add-dir` 权限、stdin 不是终端、`codex.cmd` EINVAL、stdin 挂起、here-string/UTF-8 无 BOM 把提示词写坏。提示词最终放到 `overlay/prompts/*.txt`。

6. **实时日志**  
   SSE 推 session log。开始按钮不再等完整扫盘（扫盘缓存 30 秒）。

7. **外观**  
   手搓 → Naive → PrimeVue Aura → Ant 候选 → DaisyUI glass + night。目标是暗色、毛玻璃、呼吸感，用现成组件而不是自绘皮肤。

8. **多轮对话**  
   一次 `exec` 回 `PONG` 就退是预期。补了 session id 解析、`waiting` 状态、`POST /api/codex/resume`、页面续聊框。用同一 session 从 PONG 续到 PING 验证过。

9. **经面板切换 `E:\ozdqp-main-fix`**  
   旧 attach 提示要求“有脏文件 / 内容不同就停手、不要 `-PreferLibrary`”，而 main-fix 必然脏、3 Skill 也必然和 hub 不同（官方/旧副本 vs 本地整理）。结果第一轮只会侦察然后停。  
   于是只改中心仓 `attach.txt`：面板点击视为确认；业务脏文件不是阻塞；3 Skill 不同就用 `-PreferLibrary`。  
   同一条面板会话 resume 后，**由 Codex** 跑 Disable 和 `attach-library -ConfigureGit -PreferLibrary`。实现者没有自己建链接。  
   结果：三个 Skill 指向 hub，override 硬链接到 hub，官方 `.claude/skills` 与 `.codex/skills` 不在磁盘，`attached-worktrees.txt` 含该路径，原 11 个业务脏文件仍在。旧 overlay 备份在 `.codex/local-overlay.pre-hub-20260818-181256/`。

10. **验收测试**  
    `panel/test/assert-main-fix-attached.mjs`（`npm run test:attach`）打活面板的 `/api/worktrees` 和会话日志，确认是 Codex 跑的脚本。

## 7. 明确没做、也不该做的事

- 没有把中心仓推到 GitLab，还不是团队服务
- 没有自动挂接盘上其它 worktree
- 没有自动 adopt inbox 里的官方 Skill
- 没有把 3 Skill 提交进游戏仓
- 没有在实现者自己的 shell 里替 Codex 完成第一次切换
- 没有用 `-Force` / `-PromoteFromWorktree` 把旧树内容写回 hub
- `unity-skills` 仍留在游戏工程侧
- 面板 Codex 仍然是一次性 exec + resume，不是真正的交互式 TTY
- MCP 鉴权失败（例如外部订单 MCP）只打日志，不影响挂接

当前已知的文案漂移：`AGENTS.override.md` 里对新树仍写“先侦察、等确认、再验收”；`attach.txt` 已改成“面板点击即确认”。以提示词和面板行为为准，override 那段应视为旧描述。

## 8. 以后若要做成中心服务

现在的形状已经按“以后能变成服务器”留了缝，但还差一层产品化：

1. 把 hub 推到 GitLab，多人 clone 或挂同一网络盘
2. 每台机器仍要自己起面板、自己配 Codex 登录态
3. inbox / history / sessions 要决定哪些进 Git、哪些只留本机
4. 挂接名单按人/按机器拆，不要所有人写同一份 `attached-worktrees.txt`
5. attach 对话继续当唯一的“第一次切换”入口，不要退回静默脚本

在那之前，它就是一台开发机上的本地 Skill 主库：一份 3 Skill，若干游戏树打链接，官方更新进待审箱，切换动作给人看、给 Codex 做。

## 9. 分层：适配 / 核心 / 控制

执行代码按三层切，依赖只能向内：控制 → 核心 → 适配。核心不 `import` HTTP，也不出现 `powershell.exe` / `Win32` / `APPDATA`。`skills/`、`AGENTS.override.md`、inbox 语义不因分层改写。

本阶段（查询）每层的功能、对外接口和测试见 `docs/三层本阶段规格.md`。

### 9.1 适配层

面向 OS 和外部进程。Win / Mac / Linux 只在这里分叉。

| 端口 | 要藏住的差异 |
|---|---|
| 链接 | 同盘目录：Win Junction / POSIX symlink；文件：先 symlink，Win 失败再 HardLink；用 inode/file-id 认 HardLink |
| 路径 | Win / Darwin 默认大小写不敏感；Linux 敏感 |
| 进程 | 脱离父 Job；定位 `codex` 可执行文件（尚未迁完） |
| Git | `worktree list`、`config`、`rev-parse`，核心只看结果对象 |
| 持久化 | `state.json` / `sessions.json` / `history/*.json` / 两份名单 txt |

**不进适配层：** 「第一次挂接必须走对话」「adopt 后给已挂树补链接」「业务脏文件不阻塞」。

### 9.2 核心层

一份 TypeScript 实现，对外是命令，不是再导出一堆脚本。

| 命令 | 性质 | 现状 |
|---|---|---|
| `status` | 查询 | 已迁；CLI 与 `/api/state` 共用 |
| `list-worktrees` | 查询 | 已迁；CLI 与 `/api/worktrees` 共用 |
| `list-skills` | 查询 | 已迁 |
| `repair-links` | 幂等磁盘 | 仍在 `attach-library.ps1` |
| `decide` | 幂等磁盘 | 仍在 `promote-inbox.ps1` |
| `ingest` | 幂等磁盘 | 仍在 `analyze-remote-skill-update.ps1` |
| `attach` / `detach` / `edit` / `chat` | 只入队会话 | 仍在 `panel/server/index.mjs` |

核心持有的规则：权威源在 hub；保留 3 Skill、`unity-skills`、`skills/adopted/*`；官方更新只进 inbox；已挂树断链可直接修，第一次切换只通过会话；客户端仓 = `AGENTS.md` + `baloot_client`。

### 9.3 控制层

| 入口 | 职责 |
|---|---|
| Web | 展示与拍板，只调 HTTP |
| HTTP | 把 URL 转成核心命令；SSE 只转发会话日志 |
| CLI | `npm run hub -- status` / `list-worktrees` / `list-skills` |
| Git hook | 薄触发器（仍调 `.ps1`，后续改调 CLI） |

控制层零策略。发现 handler 里出现 `if (preferLibrary)` 就是层又糊了。

```text
  Vue ──► HTTP ─┐
  CLI ──────────┼──► core（命令 + 策略）──► ports
  hook ─────────┘                              │
                                    ┌──────────┼──────────┐
                                    ▼          ▼          ▼
                                  link/fs     git      process/codex
                                  win|posix   (通用)    win|posix
```
