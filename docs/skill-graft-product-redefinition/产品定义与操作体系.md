# Skill Graft 产品定义与操作体系

## 1. 产品定义

Skill Graft 是一个“工作区技能体系管家”：它先以只读方式查看用户选定的 Windows 工作区，识别其中完整的 Skill、Agent 规则及其来源关系；用户明确选择后，将选中的内容整理为可管理的中心库，并以统一的比较、融合、版本化流程服务其他工作区。

产品要解决的不是某一个目录或某一次连接故障，而是让用户始终知道：当前发现了什么、哪些内容属于同一体系、哪些内容会被采用、哪些文件会被改动，以及出现问题后如何恢复。

### 1.1 目标用户

- 使用多个项目、分支或工作树的开发者。
- 负责团队 Skill、Agent 规则和宿主适配的维护者。
- 需要从复杂工作区提取可复用能力，但不应被内部协议词阻挡的普通使用者。
- 希望让 AI 协助维护规则，同时要求自己确认每次写入的用户。

### 1.2 核心任务（JTBD）

1. “当我第一次使用时，我想选一个文件夹并看到里面所有 Skill / Agent 体系，确认产品没有漏看或误算。”
2. “当一个工作区同时有多个入口、别名、缓存和旧版本时，我想知道它们是否是同一个来源，以及该选哪一份。”
3. “当我准备建立中心库时，我想明确决定纳入什么，并让原工作区保持不变。”
4. “当我维护中心库时，我想搜索、查看、手动修改，或让 AI 提出可审阅的修改。”
5. “当我连接另一个工作区时，我想把新内容安全融合进中心库，或明确用中心库接管它。”
6. “当已连接工作区出现上游新 Skill 时，我想沿用同一套发现、比较、融合和生成新版本的流程。”
7. “当发生冲突、取消或失败时，我想知道哪些内容已变、哪些内容保留，以及如何恢复。”
8. “当我使用助手时，我想看到正常的用户消息和 AI 回答，而不是被后台状态日志替代。”

## 2. 产品对象

### 2.1 中心库

用户确认过的 Skill / Agent 体系集合，是后续融合、接管和版本管理的参考基准。中心库不是某一个工作区的隐形镜像；它有自己的内容、来源记录和不可变版本历史。

### 2.2 工作区

用户通过 Windows 原生文件夹选择器选定的项目文件夹或工作树。首次分析和连接前分析只读访问它。工作区可能包含用户脏改、项目私有 Skill、宿主投影、链接目录、缓存和 Git index 中的缺失记录。

### 2.3 体系

产品进行选择和管理的默认单位。一套体系可包含多个 Skill、`AGENTS.md` / `CLAUDE.md` 等规则入口、清单、宿主投影及其来源关系。体系不等于一个目录，也不应只按目录名称判断。

体系通常不会很多。首次初始化默认只选择一个最适合作为中心库基线的主体系；只有分析确认工作区中存在彼此独立、服务不同项目目标的体系时，才允许同时选择多个。不同项目可以各自连接到适合自己的中心库，不要求把所有项目的 Skill 强行并入同一体系。

### 2.4 Skill

体系内可识别的能力单元。普通流程按体系选择；只有进入高级模式时才要求用户对单个 Skill 或文件作更细选择。

### 2.5 Agent 规则

影响宿主或项目行为的规则入口，例如 `AGENTS.md`、`CLAUDE.md`，以及其他合理的规则入口文件。规则应显示作用范围、来源路径和与其他入口的关系。

### 2.6 来源与关联

每个候选体系都保留来源路径、链接目标、宿主投影、内容相似度、版本差异和发现依据。来源记录用于解释“为什么被归到一起”，不表示产品已经修改或接管该路径。

### 2.7 版本

中心库在某个时刻的完整、不可变状态。版本包含父版本、变更摘要、来源依据、用户选择和生成时间。修改、融合和回滚都生成新版本，不能原地覆盖旧版本。

### 2.8 分析结果与变更预览

- **分析结果**：某次只读分析的发现，可供用户选择和比较。
- **变更预览**：一次操作在真正写入前展示的新增、修改、删除、保留、冲突和恢复边界。

## 3. 默认原则

1. **先只读，后写入。** 选择工作区和分析工作区不会修改工作区。
2. **发现完整而不增加学习成本。** 默认展示常见宿主根、任意合理的 `agent_skills`、规则入口、链接、缓存、备份、缺失记录和配置声明。
3. **按体系作决定。** 普通用户面对“纳入 / 排除 / 稍后处理”，而不是一开始面对大量文件复选框。
4. **来源可解释。** 每项都说明来自何处、与哪一项相同或相似、为什么被归并。
5. **缓存和缺失不冒充活跃来源。** Cache、PackageCache、备份目录、Git 中有记录但物理缺失的内容、配置声明但未落盘的内容均保留为发现证据，默认不纳入。
6. **私有内容由用户授权。** 系统可提示“可能是项目私有”，但未经用户明确选择不得删除、覆盖或上传。
7. **每次写入可预览、可保全、可回滚。** 接管前必须生成保护点；中心库写入必须产生新版本。
8. **融合、接管和更新共享一条认知路径。** 用户始终经历“发现变化 → 比较 → 选择处理方式 → 预览 → 应用 → 新版本 / 已连接”。
9. **AI 只提出建议。** AI 修改必须以差异和影响范围呈现，并经用户确认后应用。
10. **技术复杂度后置。** 主流程只显示“选择工作区、分析、选择、应用、已连接”；命令、事件、锁、运行记录等只在可展开的高级诊断中显示。
11. **不清理脏状态。** 用户工作区中的未提交修改、未知文件和私有内容默认保留；产品不能通过清理来获得“干净”结果。

## 4. 信息架构与主流程文案

默认导航保持少量页面：

1. **首次使用**：选择工作区 → 分析 → 选择体系 → 创建中心库 v1。
2. **首页**：先回答当前是否有新修改，再提供工作树、中心库和 AI 助手三个直接入口；首页不展示方案版本、最近活动或原则说明。
3. **中心库**：体系、Skill、规则、来源、搜索和当前版本。
4. **比较与应用**：分析结果、差异、冲突、变更预览和确认。
5. **版本历史**：版本详情、比较和恢复。
6. **AI 助手**：正常聊天、上下文、建议变更和进入预览。
7. **高级诊断**：默认隐藏，承载技术命令、事件和运行细节。

推荐主按钮文案：

- “选择工作区”
- “开始只读分析”
- “选择要纳入的体系”
- “预览中心库 v1”
- “创建中心库 v1”
- “融合进中心库”
- “使用中心库接管此工作区”
- “预览变更”
- “生成中心库新版本”
- “保存为新版本”
- “恢复为此版本”

不在默认界面出现的词：`snapshot`、`claim`、`planSync`、`Runner`、`SessionView`、`ledger`、`lock`、`typed command`、`session event`。对应显示为“本次分析”“纳入范围”“变更预览”“正在分析”“任务进度”“操作记录”“文件正在使用”“技术详情中的命令 / 事件”。

## 5. 端到端用户旅程

### 5.1 首次安装与中心库初始化

1. 欢迎页说明：“先选择一个工作区，Skill Graft 会先只读分析。”
2. 用户点击“选择工作区”，使用 Windows 原生文件夹选择器选择项目目录。
3. 页面显示所选路径和边界：“现在只会读取此文件夹及其索引记录，不会修改工作区。”
4. 用户点击“开始只读分析”；进度使用“正在查看文件、规则和链接关系”等自然语言。
5. 结果页按体系列出发现。明确的活跃来源可默认勾选；缓存、备份、缺失和疑似私有项默认不勾选。
6. 用户选择要纳入的体系，点击“预览中心库 v1”。
7. 预览显示纳入列表、来源路径、被排除的发现、原工作区保全说明。
8. 用户点击“创建中心库 v1”。写入只发生在中心库数据区，原工作区不变。
9. 完成页显示“中心库 v1 已创建”，提供“查看中心库”和“查看来源”。

### 5.2 复杂工作区分析与体系归并选择

以 `E:\ozdqp-main-fix` 作为主要设计 fixture 时，结果页至少应能表达：

- `baloot_client\.agents\skills\unity-skills` 的 UnitySkills REST 候选来源。
- 根 `.agents\skills\unity-skills` 是链接别名，不应重复计算。
- Unity MCP CLI 的 `.agents\skills`、`.cursor\skills`、`.claude\skills` 是同一后端家族的宿主投影，差异另行展示。
- `Tools\AIGameTesting\agent_skills\enter-game-hall` 可能是独立的项目私有体系。
- PackageCache 与活跃源拥有相同模块路径集合，但实测内容哈希不同；它作为同家族的缓存镜像 / 版本候选展示，不冒充第二套活跃来源，也不标记为“完全重复”。
- Git index 有记录但物理缺失的内容显示为“Git 有记录、当前缺失”。
- `skills-lock.json` 声明但未落盘的条目显示为“配置声明存在、文件未找到”。

每张体系卡片显示名称、状态、来源路径、关联原因、版本差异和“纳入 / 排除 / 稍后处理”。默认选择按体系完成；高级模式才允许选择某个宿主投影或文件版本。

### 5.3 中心库查看、手改、AI 修改、版本化与回滚

1. 中心库首页显示当前版本、体系数量、Skill 数量、来源数量和待处理变化。
2. 用户可搜索体系、Skill、规则和文件，并查看内容及来源。
3. 用户点击“自己修改”编辑中心库草稿；或点击“让 AI 协助修改”进入助手。
4. AI 或用户修改只形成草稿，页面显示变更摘要和影响范围。
5. 用户点击“预览变更”查看文件级差异、冲突和保全范围。
6. 用户点击“保存为新版本”，生成新的中心库版本。
7. 版本历史可以比较任意版本。
8. 用户点击“恢复为此版本”时，系统以旧版本内容生成一个新的恢复版本，原历史仍可查看。

### 5.4 连接工作区：融合进中心库

1. 用户在工作区首页点击“连接工作区”，用原生文件夹选择器选择目录。
2. 系统只读分析并显示与中心库的比较：新增、更新、相同、冲突和疑似私有内容。
3. 用户选择两个主要操作中的“融合进中心库”。
4. 比较页默认按体系展示，必要时再展开到 Skill 和文件。
5. 无冲突时，用户点击“预览并生成中心库新版本”。有冲突时先解决冲突。
6. 确认后生成中心库的新版本；来源工作区不被修改。
7. 系统记录该工作区与中心库版本的连接关系和已接受基线。

### 5.5 连接工作区：使用中心库接管

1. 用户在同一比较结果中选择“使用中心库接管此工作区”。
2. 预览页明确列出：将新增或更新的受管理路径、将保留的未知 / 私有 / 用户脏改内容、不会处理的内容。
3. 应用前生成可恢复保护点，并显示保护点位置和范围。
4. 用户确认后，仅对已识别为受管理范围的内容写入中心库内容。
5. 应用后重新分析并显示验证摘要。
6. 失败时自动使用保护点恢复，或提供明确的“恢复工作区”操作。
7. 完成后建立连接关系；取消确认或预览阶段退出时，工作区和中心库均不变。

### 5.6 已连接工作区出现上游新 Skill

1. 工作区卡片显示“有 3 个 Skill 被修改”，点击后进入三页更新流程。
2. 第一页只列出真正发生变化的 Skill：名称、路径、变化概要、涉及文件数，以及与当前版本的主要差异；缓存、休眠、声明缺失等证据不占据默认页面。
3. 第二页以 GitHub 提交记录的方式展开每个修改文件，显示路径、增删行数和逐行红绿差异；同页提供 AI 对话框，让用户说明保留、改写或合并要求。
4. 点击“让 AI 处理”只生成待审阅成果，不写入中心库。第三页展示每个文件的完整最终内容，并用绿色背景标出新增或修改行。
5. 成果页中的所有文件默认就是可选中、可滚动、可直接输入的编辑器，不再要求点击“直接编辑”。页面只提供一个统一 AI 输入框；用户勾选 AI 的作用文件后一次说明处理要求。人工或 AI 再次修改后，相关文件回到“待确认”。
6. 用户点击“确认并合并到中心库”后才生成新的不可变方案版本；中途“稍后处理”保留待处理提示，中心库和来源工作区均不变化。

### 5.7 冲突、取消、失败与恢复

冲突文案应说明事实，例如：“中心库和此工作区都修改了同一个规则文件。”用户可以“保留中心库版本”“使用工作区版本”“手动合并”或“跳过此体系，稍后处理”。

- 取消只读分析：不产生文件写入。
- 取消融合预览：不生成中心库新版本。
- 接管确认前取消：工作区不变。
- 接管写入失败：恢复到应用前保护点，并显示失败路径和未完成范围。
- 权限、文件占用或链接失效：显示用户可行动的重试建议，不只显示“失败”。
- 未完成操作保留可恢复的预览草稿，用户可继续处理，而不是重新理解整个任务。

### 5.8 正常 AI 聊天

聊天页必须以对话为正文。例如：

> 用户：把 Unity MCP CLI 的安装说明改成更适合新同事阅读的版本。
>
> AI：我会保留现有命令和来源说明，重写开头的安装步骤，并删除重复表述。拟修改 2 个文件。你可以先查看变更。

用户可点击“查看变更”，进入共享的变更预览，再点击“应用并保存为新版本”。AI 不能静默修改中心库或工作区。后台事件、命令、运行状态放在可展开的“技术详情”中，不能替代用户消息和 AI 回答。

## 6. 关键假设

1. Windows 原生文件夹选择器可作为默认入口；手填路径只作为高级备用入口。
2. 体系身份由路径、链接目标、内容相似度、规则入口、清单和后端元数据共同判断，不能只依赖目录名称。
3. 读取工作区的索引记录只用于分析，不执行 checkout、清理、attach 或其他隐式写入。
4. Cache、PackageCache、备份、缺失和声明未落盘项始终作为证据展示，除非用户明确纳入。
5. “可能是项目私有”是安全提示，不是系统授权；删除、覆盖和上传必须另行确认。
6. 中心库版本为追加式语义，修改、融合和恢复均产生新版本。
7. 已连接工作区可以是脏的；分析和连接不得清理用户修改。
8. 接管只写入明确识别的受管理范围，未知和私有范围默认保留。
9. 上游更新复用首次连接的分析、比较、融合和版本流程。
10. 当前生产 UI 已迁入 `panel` 的 `ProductApp`，由 `server/product-service.mjs` 提供分析、中心库、比较、草稿、版本、接管和聊天等产品 API；隔离验收仍可使用基于真实工作区线索的 fixture，但 fixture 只属于验收数据，不替代真实工作区事实。

## 7. 可验收标准

- 新用户不需要理解内部协议词，即可从“选择工作区”走到“中心库 v1 已创建”。
- 默认打开 Windows 原生文件夹选择器。
- `E:\ozdqp-main-fix` fixture 能展示活跃来源、链接别名、重复投影、缓存、休眠缺失和声明未落盘。
- 初始选择按体系完成，并可查看每项来源和归并原因。
- 连接工作区默认只有“融合进中心库”和“使用中心库接管此工作区”两个主要选择。
- 融合生成中心库新版本，来源工作区保持不变。
- 接管先展示写入范围、保全范围、保护点和回滚边界。
- 未明确选择的项目私有 Skill 不会被删除、覆盖或上传。
- 所有写入前都有变更预览和确认；取消不会留下半成品。
- 版本可以比较和恢复，恢复不会抹掉旧历史。
- 已连接工作区的新变化进入同一套分析、比较、融合流程。
- 首页只显示新修改状态、已连接工作树、中心库 Skill 总数和快速 AI 输入；三个快捷区分别进入工作区、中心库和完整对话页。
- AI 页面显示正常的用户消息和 AI 回复，技术日志默认隐藏。

## 8. 实施边界

本文件定义产品和操作体系。当前成品入口是 `panel` 导出的网页，服务端由 `server/product-service.mjs` 对接产品能力；本次真实浏览器验收使用隔离数据根和 `http://127.0.0.1:18865/`，不把安装态、旧备份或用户工作树作为写入目标。首次初始化、融合、已连接工作区更新、AI 草稿、接管与回滚已经在隔离数据根和安全 fixture 中完成真实网页点击；生产安装、任务计划、端口服务切换以及真实用户工作区写入仍以验证记录列出的未验证边界为准，不能因页面可点击就外推为生产验收。
