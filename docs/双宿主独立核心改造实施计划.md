## 1. 最终改造目标

产品最终只有一套业务能力，但有两个**对等、完整、可独立安装**的宿主发行：

| 发行 | 面向用户 | 独立安装后必须具备 | 不得依赖 |
|---|---|---|---|
| **本地发行（Local Distribution）** | Codex、Claude Code，以及插件能力不完整的编辑器 | `sg` CLI、安装与诊断、状态与工作树管理、pin/物化、inbox、会话、守护/API、独立网页、Codex Runner | DSH、DSH profile、DSH Web |
| **DSH 发行（DSH Distribution）** | 完整运行在 DeepSeek Harness 中 | DSH bundle、宿主设置与工作区适配、DSH 内页面、pin/物化、inbox、会话、DSH Runner、安装/卸载 | 外置 `sg`、本地发行的 daemon、`127.0.0.1:18765`、Codex 可执行文件 |

两者共享同一个独立核心和同一组应用命令、状态 schema、pin schema、物化规则、迁移规则。两者的差异只允许出现在：

- 宿主生命周期和依赖注入；
- 文件、Git、锁、持久化等端口的宿主实现；
- 会话如何执行（Codex 独立进程或 DSH 进程内）；
- UI、设置、安装与卸载的宿主呈现。

**关键纠正：CLI 不是唯一业务入口。** 唯一业务入口是共享的 `HubApplication.execute(command)`（最终名称可调整，但语义不得变）。本地 CLI、HTTP 和网页调用本地发行装配出的 Application；DSH 插件在进程内调用 DSH 发行装配出的同一 Application。任何宿主都不得绕过 Application 直接重写领域规则。

```text
                         共享且与宿主无关
        ┌────────────────────────────────────────────┐
        │ Contracts / Schemas                        │
        │ Domain Core + Application Commands         │
        │ pin / inventory / materialize plan / inbox │
        │ attach policy / session state / migrations │
        └──────────────────┬─────────────────────────┘
                           │ ports
              ┌────────────┴────────────┐
              ▼                         ▼
   本地发行适配与装配                 DSH 发行适配与装配
   Node fs/git/lock                  DSH workspace/settings/storage
   Codex SessionRunner               DSH in-process SessionRunner
   CLI/HTTP/daemon/panel             Cordis host/client/lifecycle
   setup/doctor/hooks                bundle install/remove
```

### 1.1 完成后的用户体验

1. 只安装本地发行：即使机器上没有 DSH，也能完整管理、同步、审查和发起会话。
2. 只安装 DSH 发行：即使机器上没有全局 `sg`、没有 18765 daemon、没有 Codex，也能在 DSH 中完整使用。
3. 两个发行同时安装：可以读取同一个 Hub 数据根，并通过同一 schema 和跨进程锁安全协作；不得互相覆盖或产生两套认领结论。
4. 同一工作树可以 pin 到稳定快照；升级核心运行时代码不自动改变该树的 Skill 内容。
5. 任何真实写入都先生成计划、检查脏改和冲突，再原子提交；失败可恢复，不把半份内容留在工作树。

### 1.2 明确不在本轮做

- 多机/团队服务、账号、云同步、GRAFT 商店。
- 自动采用官方 Skill、静默第一次 attach、强制覆盖工作树脏改。
- 把 DSH 发行做成调用外置 CLI 的壳。
- 为了新架构立即删除旧 Junction/HardLink；旧树只做受控迁移和兼容。
- 修改任何正在开发的 OZDQP 活工作树来换取测试通过。

## 2. 目标代码与包边界

最终建议收敛成以下包。迁移必须渐进进行；每一阶段都要让主分支保持可构建、可安装、可回滚，不能一次移动全部目录后再慢慢修。

```text
packages/
  contracts/                 版本化 command/result/event/state schema
  core/                      纯领域规则、计划计算、迁移决定；零宿主 API
  application/               HubApplication、用例编排、事务边界、ports
  adapters-node/             Node fs/git/process/lock/persist/materialize
  host-local/                CLI/HTTP/daemon/setup/doctor/Codex Runner 装配
  host-dsh/                  Cordis host/client、DSH adapters、DSH Runner
panel/                       本地发行网页（只经本地 host API）
test/
  contract/                  两个宿主必须共同通过
  integration/               端口与存储集成
  real/local/                本地安装真实环境
  real/dsh/                  DSH profile 真实环境
  real/cross-host/           两发行并存与锁
artifacts/verification/      只存脱敏摘要/清单；日志和密钥不入库
```

如果阶段内暂时保留 `src/core` / `src/adapters`，也必须通过导出边界达到同样效果，再在后续阶段机械迁包。目录名不是完成标准，依赖方向和真实可运行性才是。

### 2.1 共享层允许和禁止的依赖

| 层 | 允许 | 禁止 |
|---|---|---|
| contracts | TypeScript 类型、可移植 schema/校验库 | Node fs/http/process、React、Cordis、Codex、环境变量 |
| core | contracts、纯函数、领域值对象 | Node/Win32、DSH/Cordis、CLI argv、HTTP、UI、安装路径 |
| application | core/contracts、声明的 ports、事务协调 | 直接 `fs`/`git`、`powershell.exe`、`ctx.*`、DOM |
| local adapters/host | Node/PowerShell/Codex/HTTP/网页协议 | 复制一份领域规则或私有 schema |
| DSH adapters/host | Cordis、DSH host/client services | 外置 `sg`/18765 作为运行前提、复制一份领域规则 |

### 2.2 统一应用命令合同

Application 至少要统一承载：

- 查询：`status`、`listSkills`、`listWorktrees`、`getPin`、`planSync`、`session`；
- 写入：`sync`、`setPin`、`attach`、`detach`、`repairLegacy`、`ingest`、`decide`；
- 会话：`startSession`、`resumeSession`、`cancelSession`；
- 迁移：`inspectSchema`、`migrateState`。

每个命令必须返回带版本的结构化结果，不得靠 stdout 文本给 DSH 解析。CLI 只是把结构化结果编码为 JSON/人类文本；DSH 直接消费对象。

## 3. 版本、pin、物化与并发合同

这部分必须在接两个宿主之前定死，否则两个发行会各自发明状态。

### 3.1 两类版本不得混为一个 Git HEAD

当前公开仓默认不跟踪 `skills/**`，所以工作树 pin 不能简单等于运行时仓库的 Git HEAD。必须拆成：

| 字段 | 含义 | 示例 |
|---|---|---|
| `runtimeRevision` | 运行时/Application/适配代码版本 | npm/package version + 可选 Git SHA |
| `librarySnapshot` | Skill 与 override 内容快照 | 内容寻址 SHA-256 或显式 snapshot ID |
| `schemaVersion` | 状态和 pin 的迁移版本 | 整数，迁移只能单向显式执行 |

`librarySnapshot` 必须能独立验证内容清单，至少记录文件相对路径、大小、摘要和来源。pin 指向 snapshot，不指向某个当时恰好存在的工作目录。

### 3.2 建议的持久化对象

```text
HubStateV2
  schemaVersion
  runtimeRevision
  librarySnapshots[]
  worktrees[pathKey]
    requestedSnapshot
    materializedSnapshot
    selectedSkills[]
    claimState
    lastPlan
    lastResult
  inboxItems[]
  sessions[]
```

约束：

- `pathKey` 由平台适配标准化，Windows 必须处理盘符和大小写。
- `requestedSnapshot` 与 `materializedSnapshot` 分开，失败不能假装已同步。
- pin 更新和物化完成分别落审计事件。
- JSON 写入使用临时文件 + flush + rename；进程崩溃后要么旧状态完整，要么新状态完整。
- 本地发行与 DSH 发行共用同一锁协议和锁目录；锁记录持有者、宿主、PID、命令、起始时间和租约。

### 3.3 物化安全合同

`planSync` 必须是无副作用的，输出至少包括 `create/update/delete/keep/conflict`。`sync` 只能执行已重新校验的计划：

1. 读取 pin 与 snapshot manifest；
2. 取得对应工作树的跨进程独占锁；
3. 再次计算盘上摘要，识别用户脏改；
4. 在同卷临时目录准备完整目标；
5. 原子替换可控文件；
6. 写入 materialized marker 和状态事件；
7. 释放锁；
8. 任一步失败都回滚临时内容，并保留原副本。

`unity-skills` 和项目拥有的非 Hub Skill 永不删除。旧链接先识别，再由明确的 `repairLegacy`/迁移流程处理；普通 `sync` 不暗中拆链接。

## 5. 真实测试环境总设计

### 5.1 本地发行隔离环境

新增可重复脚本创建独立根，例如：

```text
E:\skill-graft-e2e\local-<run-id>\
  app\               npm pack 后安装的本地发行
  home\              隔离 HOME/APPDATA 等宿主数据
  hub-data\          隔离 HubState、snapshot、locks
  probe\             从固定 fixture/稀疏 worktree 建出的可写探针
  logs\
```

要求：

- 测试运行必须显式传 `SKILL_GRAFT_HOME`（名称可在 P2 最终确定），不得读写真实 Hub 数据根。
- 通过 `npm pack` 产出的 tarball 安装，不能只在源码树里 `node dist/...`。
- 实际执行 `sg setup`、`sg doctor`、`sg status`、`sg sync`，启动 daemon/API/网页并从浏览器或 HTTP 完成至少一条写路径。
- Codex 验收使用专用探针和清晰可终止的提示词；记录真实会话 ID、状态和目标文件结果。
- 测试完验证卸载与进程退出；只清理本次明确 run-id 目录。

现有 `E:\ozdqp-cli-attach-probe` 可作为人工最终探针，但自动流程优先生成每轮隔离副本，避免并发任务互相污染。

### 5.2 DSH 发行隔离环境

必须使用本机源码 `E:\deepseek-harness-master` 和独立 `DSH_HOME`，不能污染用户日常 `~/.dsh`：

```powershell
$env:DSH_HOME = 'E:\skill-graft-e2e\dsh-<run-id>\home'
$env:SKILL_GRAFT_HOME = 'E:\skill-graft-e2e\dsh-<run-id>\hub-data'
Set-Location 'E:\deepseek-harness-master'
pnpm run build
pnpm run dsh plugin --profile web add <host-dsh-tarball-or-path>
pnpm run dsh --profile web --dump-config
pnpm run dsh --profile web --port 0
```

实际命令在 P6 根据 bundle 最终 profile 形式固化；上面是验收方向。必须证明：

- profile 中确实安装并激活 `dsh.bundle`，不是普通依赖；
- `--dump-config` 能看到 Host 插件行和 Client 插件声明；
- DSH Web 真正启动在隔离端口，插件设置页/工作区页可交互；
- 临时移除 PATH 中的全局 `sg`，停止本地 daemon 后，DSH 发行仍能执行 status、pin、sync、inbox 和会话；
- `dsh plugin --profile web remove <package>` 后配置、页面和后台资源均消失，Hub 数据按卸载策略保留或明确删除。这里的 `web` 位于本轮隔离 `DSH_HOME`，不会触碰日常 profile。

### 5.3 双宿主并存环境

本地发行和 DSH 发行指向同一个隔离 `SKILL_GRAFT_HOME`，但用不同宿主 ID。至少验证：

1. 本地发行写 pin，DSH 立即按 schema 正确读取；反向也成立。
2. 本地 `sync` 与 DSH `sync` 同时发起，只有一个持锁执行，另一个收到结构化 busy/retry 结果。
3. 一方在旧 schema 上启动时拒绝危险写入并提示迁移，不得偷偷降级状态。
4. 一方崩溃或被终止后，租约超时/进程存活检查能恢复锁；工作树内容仍为完整旧版或完整新版。
5. 两个发行生成一致的 `planSync` 和冲突分类。

## 8. 执行中的永久安全规则

1. 不改 OZDQP 活工作树；真实写入只进 run-id 隔离环境或明确的 attach probe。
2. 不运行会修改真实 probe 的测试，除非命令名含 `test:real`、显式开关已设置且目标绝对路径通过边界校验。
3. 不提交 `skills/**`、会话全文、credentials、`skill-review/history`、本地状态和测试临时目录。
4. 不用单测或 mock 声称安装、UI、进程、DSH profile、Codex/DSH 会话已经验收。
5. 每阶段必须真实构建发布形态：本地发行用 `npm pack` 后安装；DSH 发行用真实 `dsh plugin --profile ... add` 后启动。
6. DSH 发行不得以外置 CLI/daemon 为必要条件；本地发行不得以 DSH 为必要条件。
7. shared core/application 禁止任何 Codex、DSH、Cordis、HTTP、DOM、Win32 分支。
8. 未成功推送并核对远端 SHA，不开始下一阶段。
